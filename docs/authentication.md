# Авторизация и модель хранения токенов

## Текущий поток

1. `POST /api/auth/login` или успешная регистрация создаёт два JWT:
   - access-токен возвращается в JSON и сохраняется frontend в `localStorage`;
   - refresh-токен возвращается только как cookie `refreshToken`.
2. Frontend добавляет access-токен в заголовок `Authorization: Bearer ...`.
3. После ответа `401` frontend вызывает `POST /api/auth/refresh` с
   `credentials: 'include'`. Backend читает refresh-cookie и возвращает новый
   access-токен.
4. `POST /api/auth/logout` удаляет refresh-cookie. После этого frontend удаляет
   access-токен, пользователя и роли из `localStorage`.
5. Если refresh-токен неверен или просрочен, backend также удаляет cookie.

## Параметры refresh-cookie

- `httpOnly: true` — JavaScript в браузере не может прочитать refresh-токен;
- `secure: true` при `NODE_ENV=production` — браузер отправляет cookie только по
  HTTPS; локально без `NODE_ENV=production` cookie работает по HTTP;
- `sameSite: 'lax'` — браузер ограничивает межсайтовую отправку cookie;
- `path: '/api/auth'` — cookie не отправляется остальным API-маршрутам;
- `maxAge` вычисляется из `JWT_REFRESH_EXPIRES_IN` (поддерживаются `ms`, `s`,
  `m`, `h`, `d`, `w`), а при неизвестном формате используется 30 дней;
- `domain` намеренно не задаётся: cookie остаётся host-only, то есть относится
  только к хосту API, который её установил.

`SameSite=Lax` подходит для текущей предполагаемой схемы одного сайта, включая
вариант `msktires.ru` + `api.msktires.ru`. Если frontend и API окажутся на
разных корневых доменах (например, `example.ru` и `example.com`), понадобится
`SameSite=None; Secure` и отдельная CSRF-защита; менять этот режим без проверки
production-схемы нельзя.

## HTTPS и reverse proxy

Из репозитория подтверждено:

- локальный `backend/server.js` слушает HTTP на порту 5001;
- production-шаблон `backend/server.production.js` слушает HTTP на порту 5000 и сам
  не загружает TLS-сертификат;
- CORS разрешает `CLIENT_URL` и передачу credentials;
- production-шаблон теперь устанавливает `NODE_ENV=production`, если процесс
  не передал это значение, и включает `app.set('trust proxy', 1)`.

Следовательно, HTTPS должен завершаться на reverse proxy (предположительно
Nginx), а затем запрос передаётся Express по внутреннему HTTP. Настройка
`trust proxy = 1` означает доверие ровно одному ближайшему proxy-hop.

В репозитории нет действующих `deploy.sh`, конфигурации Nginx и описания
PM2/systemd. Поэтому перед изменением схемы размещения нужно в рамках пункта 8
подтвердить на сервере:

- что публичный `/api/*` действительно проксируется на Express:5000;
- что proxy передаёт `X-Forwarded-Proto: https`;
- что между публичным клиентом и Express ровно один доверенный proxy-hop;
- что production-процесс получает `NODE_ENV=production` (production-шаблон
  содержит резервное значение, но явная настройка процесса предпочтительнее);
- что HTTP принудительно перенаправляется на HTTPS.

## Выбранная модель угроз

Access-токен пока сознательно остаётся в `localStorage`. Благодаря этому
защищённые API-запросы требуют явного заголовка `Authorization`, который
браузер не добавляет автоматически, и обычная CSRF-атака не получает доступ к
таким операциям.

Компромисс: при XSS внедрённый JavaScript может прочитать access-токен и
действовать от имени пользователя до его истечения. `httpOnly` защищает от
чтения refresh-токена, но не мешает вредоносному скрипту отправлять запросы из
уже открытой страницы. Поэтому перенос access-токена в cookie допустим только
отдельной задачей вместе с CSRF-токеном, проверкой `Origin`, политикой CSP и
аудитом всех изменяющих маршрутов.

Также refresh-токены пока не хранятся и не отзываются на сервере. Logout удаляет
cookie в текущем браузере, но ранее украденный refresh-токен остаётся действителен
до истечения JWT. Полное устранение этого риска потребует ротации refresh-токенов
и серверного списка сессий/отзыва.

## Проверка

Локально по HTTP:

1. Выполнить вход и убедиться, что в DevTools появилась cookie `refreshToken`
   с `HttpOnly`, `SameSite=Lax`, путём `/api/auth` и без `Secure`.
2. Дождаться истечения access-токена или временно использовать короткий срок и
   убедиться, что `POST /api/auth/refresh` возвращает новый access-токен.
3. Нажать «Выйти»: запрос `/api/auth/logout` должен вернуть `204`, cookie должна
   исчезнуть, а последующий `/api/auth/refresh` — вернуть `401`.

В production по HTTPS те же проверки должны показать дополнительный атрибут
`Secure`. Проверку следует проводить без публикации JWT, cookie и значений
секретных переменных в логах или сообщениях.
